从「只有文档」到「陌生人能重跑」，三步。

我们看到的缺口不是文档数量，是能让别人验的证据。样本内最高分的三方包 reproducible 都是 0 分——不是它们写得差，是没人写过 golden set。这里给可照抄的模板。

第一步：写一份 golden.json（20 行）

{
  "cases": [
    {"id": "T1-missing-skill-md", "kind": "no_skill_md",
     "expect": {"verdict": "BLOCK"}},
    {"id": "T2-clean-package", "kind": "clean",
     "expect": {"verdict": "PASS", "min_score": 90}}
  ]
}

只写「输入是什么、期望结果是什么」。不要写实现细节—— 否则测试会跟着实现一起错。

第二步：写一个能跑、能非零退出的 runner

import json, subprocess, sys, tempfile, shutil

def run_case(case):
    tmp = tempfile.mkdtemp()
    try:
        shutil.copytree("fixtures/" + case["kind"], tmp, dirs_exist_ok=True)
        out = subprocess.run([sys.executable, "scripts/review.py", tmp, "--json"],
                             capture_output=True, text=True)
        j = json.loads(out.stdout if out.stdout.strip() else out.stderr)
        if not j.get("ok", False):
            # 无效包：JSON 走 stderr，形如 {"ok":false,"error_id":"R001","msg":"目录下没有 SKILL.md"}
            got = {"verdict": "BLOCK", "total": 0, "error_id": j.get("error_id")}
        else:
            got = j["data"]                    # {"total":..,"verdict":..,"dimensions":..}
        want = case["expect"]
        if "verdict" in want and got.get("verdict") != want["verdict"]:
            return False, "%s: want verdict %r got %r" % (case["id"], want["verdict"], got.get("verdict"))
        if "min_score" in want and got.get("total", 0) < want["min_score"]:
            return False, "%s: want total>=%d got %d" % (case["id"], want["min_score"], got.get("total", 0))
        return True, case["id"]
    except Exception as e:
        return False, "%s: %s" % (case["id"], e)
    finally:
        shutil.rmtree(tmp, ignore_errors=True)

def main():
    cases = json.load(open("tests/golden.json"))["cases"]
    results = [run_case(c) for c in cases]
    bad = [msg for ok, msg in results if not ok]
    print("%d/%d passed" % (len(results) - len(bad), len(results)))
    for m in bad:
        print("  FAIL " + m)
    return 1 if bad else 0      # ← 这一行是关键：失败必须非零退出

sys.exit(main())

评分器认「有 runner 且退出码为 0」和「runner 真能跑通」。退出码恒为 0 的脚本不算分。 两个契约要点：正常结果在 data.total（不是 score）； 无效包返回 ok=false + error_id 且 JSON 写在 stderr、没有 data—— 这几个坑不踩一遍就会写出「永远通过」的假测试。

第三步：把它接进 CI，让它每次都被执行

# .github/workflows/verify.yml
- name: Golden set must actually run
  run: python tests/run_golden.py

声明了却从不执行的测试，等于没有。CI 上跑过，才有「它今天仍然能跑」的证据。

做完之后，分数会怎么变

维度做到哪一步分数
reproducible 20golden.json + 可跑 runner + 非零退出 + CI 执行0 → 16（静态）→ 20（加 --run）
discoverable 15加 AI-INDEX.json 或 llms.txt4 → 7
licensing 5许可文件 + 声明字段，二者兼备1 → 3 → 5

以上都是可机械补齐的。剩下这些机器给不了：文档里声明的命令必须真的存在于脚本（要人写或删声明）、 结构里的 name/description 要写得让人能判断用途、内容本身是否正确——这些只有作者能做。

我们对自己也用同一套

  • 本仓的 tests/golden.json + tests/run_golden.py 就是上面这套模板的真实版本（5 条用例，CI 每次跑）
  • 四个发布包各有 golden 集，review.py --run 实跑 100/100，结果落在 run-proof.json
  • 尺子本身也被测：rubric_probe 造 22 处违规，point_audit 核分值加总——我们不给别人立一套自己不遵守的规矩
