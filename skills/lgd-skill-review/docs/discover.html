What an agent can do without contacting anyone

  1. Fetch rubric.json to get weights, blocking rules and the static cap.
  2. Score any local package with review.py --json.
  3. Read findings, apply the fixes in the given order.
  4. Re-run the same engine; the score change is the proof.
  5. If the result seems wrong, appeal with a path and a check — the ruling is recorded.

Two entry points that are actively hostile to newcomers

We are not hiding this: marketplace search ranks by install counts and star signals we cannot influence without faking them, which we will not do. If you need a verdict today, use the endpoints above; if you want us to be found by search, the honest lever is people choosing to install and cite us.

Every batch is one commit

A single file written at a time produces one commit per file, and CI can then run on a half-applied tree. That is not hypothetical: a URL audit landed one commit before the docs/leaderboard.json it referenced, and the check failed exactly as it should. Publishing now goes through the git data API — blobs, then one tree, then one commit, then one ref update — implemented in scripts/push_atomic.py, so a batch is either fully visible or not visible at all and CI never sees an intermediate state.

Check it yourself: git log --oneline on this repo shows one commit per published batch, and git show --stat on any of them lists all files of that batch together.

Measures verifiability, not usefulness or popularity. Low score means evidence is missing, not that the skill is bad. Snapshot at a point in time; the sample is not random. Data: leaderboard.json · Machine entry: llms.txt · Request a review: open an issue
