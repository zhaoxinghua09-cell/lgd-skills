# 申诉规则（Appeal）

一个评测器如果只输出结论、不接受反驳，它的分数就只是意见。这份文件定义申诉怎么提、引擎怎么裁、以及**为什么裁决不改分**。

## 一、申诉能做什么，不能做什么

| 能做 | 不能做 |
|---|---|
| 指出某条扣分的**依据不成立**（例如说"没有测试"，而测试确实在） | 要求把分数改高 |
| 提供可核验的路径与验证方式 | 靠说明、承诺、口头解释推翻判定 |
| 留下可审计的记录 | 撤回已经公开发布的评测结论 |

**裁决不改分。** 引擎不会因为你说得有理就给你加分——那等于自己改自己刚给的答案，不叫翻案。申诉的作用是把一个扣分点变成可核验的争议点，由证据回答；分数要变，只能靠复测时那个依据本身不再成立。

## 二、怎么提

写一个 JSON，用 `--appeal` 传入：

```bash
python scripts/review.py <包目录> --appeal appeal.json
```

格式：

```json
{
  "items": [
    {
      "id": "R03",
      "claim": "测试执行器真实存在，只是命名不在 tests/run_*.py 的规则内",
      "path": "tests/test_runner.py",
      "expect": "file_exists"
    }
  ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 报告里整改项的 ID（R01、R02…；类型建议是 T01…）。**只在同一份报告内有效**，换一次评测就会重排 |
| `claim` | 建议 | 你的主张，写清"哪条判定错了、为什么" |
| `path` | 是 | 证据文件，相对包根目录 |
| `expect` | 否 | `file_exists`（默认）/ `contains:<文本>` / `regex:<正则>` |

## 三、引擎怎么裁

三种结果：

| 裁决 | 含义 | 触发条件 |
|---|---|---|
| **OVERTURNED** | 原判定依据不成立 | 所述路径存在，且满足 `expect` |
| **UPHELD** | 维持原判 | 路径不存在 / 文件不含所述内容 / 未提供路径 |
| **UNKNOWN_ID** | 申诉无效 | 报告里没有这个 ID（多半引用了别的报告） |

**举证责任在申诉方。** 只说"你说错了"不够，必须给一个引擎能自己去打开、去读、去匹配的东西。

## 四、留痕

每次裁决追加到包内的 `appeal_log.json`：

```json
[
  {
    "root": "my-skill",
    "at": "2026-11-18T16:58:09",
    "items": [
      {"id": "R03", "claim": "...", "verdict": "OVERTURNED", "reason": "文件存在且包含所述内容"}
    ]
  }
]
```

这份日志是公开的。任何人可以查：谁申诉过、拿什么证据、裁了什么。**没有这份日志，"接受申诉"就只是话术。**

## 五、已知限制

1. **ID 不跨报告**。整改项按输出顺序编号，包一改、规则一调，编号就会变。申诉必须针对同一份报告提出。
2. **只核验文件层证据**。能回答"这个文件在不在、里面有没有这句话"，不能回答"这段代码写得对不对"。
3. **裁决不触发复评**。推翻之后需要自己重跑一次，看那个维度是否真的变了——因为规则可能还有别的依据在支撑同一个扣分。
4. **不处理主观分歧**。你认为"这条规则本身不合理"，那是规则问题，走 issue，不走申诉。

## 六、申诉机制带来的第一批改进

这个机制上线第一天就抓到一个真实缺陷：

- 申诉："`tests/test_runner.py` 真实存在，但被判'无测试执行器'"
- 裁决：**OVERTURNED**
- 修复：`d_reproducible` 原来只认 `tests/run_*.py`，改为同时认 `run_*.py` / `test_*.py` / `*_test.py` / `run_tests.py`，并在实跑时优先选 `run_` 前缀

这条规则此前会冤枉所有用 pytest 标准命名的包——而那恰恰是最常见的一类。

**一个能被申诉的评测器，会不断被申诉改好。不能申诉的，只会一直错下去。**

# 口径修正史与常见误判

这份文件记录本评测器**自己被推翻过五次**的经过。放在这里不是为了自证清白，是因为一个评测器的可信度取决于它敢不敢记录自己的错误。

## 五次误判，全部是尺子的问题，没有一次是被测包的问题

| 轮次 | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | 从全文提取 `--flag` 判"文档承诺的命令脚本没实现" | 把「示例里出现的参数」当成「承诺的参数」，冤枉了外部包 | 只从命令块里取参数，且要求脚本 argparse 实际支持 |
| 2 | `version: "2.3.1"` 引号包裹判 SemVer 失败 | 合规的写法被判不合规 | 解析后统一去掉成对引号 |
| 3 | 邮箱出现在 Contact / 安全报告语境判 `secret_leak` | 作者主动公开的联系方式被算泄露，三包 hygiene 掉到 7/15 | 语境判定：主动公开的联系邮箱不计泄露，只保留提示 |
| 3b | 上面的修法没生效 | 判断写成 `label.startswith("email")`，而实际 label 是中文「疑似真实邮箱」，分支永不命中 | 改为 `"邮箱" in label or "email" in label.lower()` |
| 4 | `narration = 100 - 示例 - 步骤 - 规则` | 一行可同时命中多类，被重复扣减，说明性虚高约 25 个百分点 | 改为逐行直接统计 |
| 5 | YAML frontmatter 计入说明性 | 同一内容被 D4 与 D1 收两次钱；且 frontmatter 行数固定，包越小被压分越狠 | 统计前先剥离 frontmatter |

**这五次里有三次会让被测方吃亏**（第 1、3、4、5 轮），两次会让不合规的包过关（第 2 轮）。也就是说，这把尺子既会冤枉人，也会放过人。任何只看分数的结论都要带上这个前提。

## 常见误判的识别方法

**怀疑自己被误判时，按这个顺序查：**

1. **看判定依据是否给了原文位置**。只给结论不给行号的，先怀疑。
2. **看是不是"文档有、脚本没有"**。这是最真的一类问题，也最容易误判——示例里的参数不算承诺，只有写在命令清单里的才算。
3. **看卫生项命中的是不是公开信息**。作者在 SECURITY.md 里留的联系邮箱不是泄露。
4. **看分数是否被单一项拖垮**。一维归零通常是规则写错了，不是包真的差。
5. **看同一份代码量不同对象时的排序是否稳定**。换一个包、换一个语言，结论就翻转的，多半是启发式在拟合特定写法。

## 本评测器的已知边界

- 六维是**启发式规则**，不是 LLM 判定，不理解语义，只看结构证据。
- 八维（120 分制）是**按 skill-judge 的维度定义自实现的近似**，不是它的官方算法，更不是官方分数。
- 它能量出「可验证交付」的强弱，量不出「行业判断的深浅」。
- 同一方既是尺子又是被测时，分数再高也只说明「符合这套尺子」。要更强的独立性，得让第三方拿这套工具量你。

## 什么时候不该信这个分数

- 被测包是**非英文/非中文**时（正则按中英写）。
- 被测包把大量内容放在**图片、PDF 或二进制**里时（只读文本）。
- 被测包的**真正价值在语义质量**（如写作、策略、判断）而不是结构时。
- 需要判断**是否适合某个具体业务场景**时——那是人的判断，不是尺子的判断。

# 评分细则（可对外引用）

本文件是 `review.py` 的判定口径说明。对外解释分数时引用本文，不临场编标准。

## 权重

| 维度 | 权重 | 一句话 |
|---|---|---|
| structure | 20 | 包能不能被平台正确解析 |
| consistency | 25 | 文档说的，代码里有没有 |
| reproducible | 20 | 别人能不能复跑出同样的结果 |
| hygiene | 15 | 有没有把不该外泄的东西带出去 |
| discoverable | 15 | AI 能不能搜到、能不能路由 |
| licensing | 5 | 谁写的、能不能用，是否说清 |

## 逐维细则

### structure（20）

| 检查点 | 分值 | 判定 |
|---|---|---|
| name / description / version 齐备 | 6 | 缺任一为 0 |
| version 为 `x.y.z` | 4 | `1.0`、`1.2.3.4` 均不通过 |
| 目录层级 ≤ 3 段 | 4 | 出现 `a/b/c/d` 即扣满 |
| 无 .pyc / .zip / `__pycache__` | 3 | 出现即 0 |
| 有展示名 | 3 | display_name 或 displayName 任一 |

### consistency（25）——本技能的核心维度

做四件事：

1. 从 `description` 与 `SKILL.md` 提取所有 `--flag` 与 `scripts/*.py <子命令>` 声明；
2. 从 `scripts/*.py` 提取真实的 `add_argument("--x")` 与 `add_parser("x")`；
3. 比对：声明了但没实现的 → **阻断项 `declared_command_missing`**；
4. 命中文档含「不编造 / faithful」类承诺 → 加分。

为什么设成阻断：这类缺陷人眼查不出，但使用者第一次照文档调用就会失败，属于最伤信任的一类。

### reproducible（20）

| 检查点 | 分值 |
|---|---|
| 有 `tests/*.json` 用例 | 6 |
| 有 `tests/run_*.py` 执行器 | 6 |
| 有 `demo/` | 4 |
| `--run` 实跑退出码为 0 | 4 |

不实跑时最后 4 分不给——"声称有测试"和"测试真能跑"是两件事。

### hygiene（15）

- 扫描 `sk-*` / 手机号 / 真实邮箱 / 本机绝对路径，命中 → **阻断项 `secret_leak`**（8 分归零）；
- SKILL.md 有安全边界或降级声明 → 7 分。

### discoverable（15）

tags ≥3（5）、有触发词段（4）、有互链段（3）、有 `ai-index.json` 或 `llms.txt`（3）。

### licensing（5）

author（2）、license 字段（2）、独立 LICENSE 文件（1）。

## 判定线

| 条件 | 判定 |
|---|---|
| 有任一阻断项 | **BLOCK**（分数再高也不给过） |
| 总分 < 60 | FAIL |
| 60 ≤ 总分 < 80 | WARN |
| ≥ 80 | PASS |

## 类型策略（P2 建议，不参与计分）

同一套尺子量所有包，但不同类型该有的东西不同。评测器先判类型（自动识别或 `--type` 指定），
再检查「该类该有但没有」的项，输出为 P2 建议。

**为什么不并入分数**：把类型期望算进总分，等于用类型给分数注水——同一份包换个类型声明就能多拿几分。
所以我们只把它当建议列出来，分数仍由六维固定口径决定。

| 类型 | 该有 | 缺了会怎样 |
|---|---|---|
| `meeting` | 来源适配说明 / 证据溯源 / 黄金集 | 只能吃一种导出格式；数字无法核验 |
| `debug` | 证据纪律声明 / 复现分级 / 失败样例 | 输出像样但错误的原因 |
| `content` | 红线单列 / 不作虚假承诺 | 踩线、承诺阅读量 |
| `reviewer` | 自检套件 / 口径公开 / 闭环演示 | 评测器本身不可信 |
| `general` | — | — |

自动识别规则：两处文本里（description 三字段 + SKILL.md 全文）该类关键词命中 ≥2 才判定，否则归 `general`。

## 已知局限（必须说明）

- 静态检查，不做语义级代码审查；脚本内部逻辑错误查不出。
- `--run` 只认退出码，不判断测试本身是否覆盖关键路径。
- 对「文档写得极详尽但实现空洞」的包，本技能只能查出参数不匹配，查不出概念空洞。
- 分数是启发式，不替代人工终审。
